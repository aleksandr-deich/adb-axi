# Testing changes to adb-axi

1. **Start with the user-visible contract.** Before fixing a bug, reproduce it through the shipped CLI and record the failing result; repeat the same flow after the fix. Establish the expected result from the reported problem, documented contract, Android behavior or independently observed device state, never by copying the implementation's output.
2. **Use the packed-CLI real-emulator suite as primary evidence for Android behavior, including failures.** Check results against probe state, package-manager facts, kernel processes, window focus, logcat or file/database contents. Run the relevant scenario on API 29, 30 and 35; a green host suite alone does not establish Android correctness. Use only reserved disposable emulators; the full suite reboots and shuts down its target.
3. **Keep focused host unit tests for pure parsing, formatting and algorithms.** Prefer captured Android output with provenance. Do not add an adapter test that merely restates an E2E result or constructs the exact output the implementation expects.
4. **Use fake adb only for a boundary fault or environment the matrix cannot reproduce reliably and safely.** State the obstacle and the independent expected result. Hostile host inputs and unavailable external-tool protocols may need host-only evidence. Test each shared fault path once; add a command-specific case only when its recovery, safety or error contract is genuinely different. Ordinary flows, a second Android user and a missing CI tool are not inherently impossible on an emulator: document any exception rather than calling it E2E coverage.
5. **Assert outcomes, not choreography.** Do not assert an exact adb sequence or call count. Negative assertions protecting a safety contract, such as never mutating a different user's app or never sending untrusted input to a shell, are appropriate. Observe the protected effect where possible.
6. **Do not multiply behavioral cases by output format, command or API when they exercise the same path.** Test shared JSON/TOON rendering once; retain a focused case for a genuinely distinct serialization contract, such as shell stream shape. Moving a format loop inside one test is not deduplication. Parameterize only independently meaningful inputs or outcomes.
7. **Justify a new case before writing it.** Explain what regression or contract it protects, how you know the expected result is correct (for example, a probe log or a known database row), what existing checks miss and why this is the right test layer. Extend an existing scenario when practical. Do not build a new harness just to raise test counts.
8. **Retire tests only with a contract map and passing replacement evidence.** Account for safety, error and branch assertions, not just a matching command name. Preserve deterministic fault coverage when a real scenario accepts multiple platform outcomes. Do not delete, weaken or skip a check merely to get green. Explain a skip's cause, missing evidence and removal condition; prefer fixing the stimulus or moving an intentional manual-only prerequisite to a documented release check.
9. **Report evidence honestly.** Run the existing required checks (`npm run check`, plus relevant device CI). Report actual counts by layer, skips, matrix results and unresolved failures. Classify product, test and infrastructure failures separately; canceled jobs and evolving branches are not a flakiness denominator. Poll observable state with bounded deadlines, not fixed readiness sleeps, and retain transcripts for diagnosis.
